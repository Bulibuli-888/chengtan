# 抢票接口压测报告

> 所有数字都是本机实测，脚本在 `scripts/loadtest.py`，可一键复现。**没有估算、没有"百万连接"这类没测过的说法。**

## 1. 环境与方法

| 项 | 值 |
|---|---|
| 机器 | 单机 Windows，CPU/内存与压测同机（客户端和服务端抢同一份资源） |
| 服务端 | JDK 17，Spring Boot 3.5，Tomcat max-threads 400，Hikari 40 连接 |
| 中间件 | MySQL 8.0、Redis 7、RabbitMQ 3.13.7，全部本机 |
| 客户端 | `scripts/loadtest.py`，Python 标准库，每请求一个短连接 |
| 被测接口 | `POST /api/orders`（Lua 扣库存 → 落本地消息表 → 发 MQ → 异步消费建单） |

脚本做的事：

1. 用 `mysql` / `redis-cli` 建一个隔离场次（容量 = 库存）和 N 个用户 token；
2. N 个线程同时发起抢票请求，记录每个请求的耗时与业务码；
3. 等异步消费者落库后，用**单条 SQL** 同时读 `sold` 与订单数，连续两次稳定才判定结束；
4. 校验成功数 = 容量、订单数 = 容量、无超卖；
5. 默认跑完清理夹具。

指标口径：QPS = 总请求数 / 总墙钟时间（包含被拒绝的请求）；延迟为客户端观测的端到端耗时。

```bash
set MYSQL_PASSWORD=xxx
set REDIS_PASSWORD=xxx
python scripts/loadtest.py --users 300 --capacity 200
```

## 2. 结果

| 并发 | 库存 | 成功 | 拒绝（B1001 余票不足） | QPS | P50 | P90 | P99 | 超卖 |
|---|---|---|---|---|---|---|---|---|
| 50 | 50 | 50 | 0 | 254 | 82ms | 138ms | 187ms | 否 |
| 100 | 100 | 100 | 0 | 366 | 81ms | 103ms | 182ms | 否 |
| 200 | 200 | 200 | 0 | 547 | 79ms | 95ms | 180ms | 否 |
| 300 | 200 | 200 | 100 | 818 / 901（两次） | 66~76ms | 94~113ms | 161~168ms | 否 |
| 500 | 400 | 400 | 100 | 966 / 994（两次） | 67~113ms | 89~157ms | 168~190ms | 否 |
| 300（**冷启动首跑**） | 200 | 200 | 100 | **178** | **1151ms** | 1261ms | 1642ms | 否 |

一致性校验（每一轮都通过）：

- 接口返回成功数 = 最终订单数 = DB `sold` = 场次容量
- Redis 库存最终为 `0`
- 超出库存的请求全部在 Lua 层被拒绝，没有产生订单，也没有二次扣减

## 3. 三个真实结论

### 3.1 冷启动数据不能拿来写简历

同一个 300 并发场景，**应用刚启动时首跑 178 QPS / P99 1.6s，预热后复跑 818 QPS / P99 168ms**，相差 4.6 倍。

原因是 JIT 编译、连接池填充、Tomcat 线程池扩容都需要时间。第一次跑出来的数字如果不标注"冷启动"，就是自欺欺人。**面试时主动说明这一点，比报一个漂亮数字可信得多。**

### 3.2 瓶颈在客户端，不在服务端

并发从 50 涨到 500，QPS 从 254 涨到 994，延迟基本平稳（P50 67~113ms），说明服务端还没到饱和点。真正的限制是：

- 压测客户端是 Python，500 个线程共享一把 GIL，序列化/解析 JSON 本身就在抢 CPU；
- 每个请求新建 TCP 连接（没有 keep-alive），握手成本进入延迟；
- 客户端与服务端同机，CPU 互相挤占。

要继续往上压，正确的做法是换 Gatling/JMeter 多机施压、客户端开长连接，而不是改业务代码。

### 3.3 接口耗时构成

单次抢票在服务端要做四件事：Redis 执行 Lua（微秒级）→ 查库校验出行人归属 → 写本地消息表 → **同步等待 RabbitMQ Publisher Confirm**。

其中最后一步是唯一跨网络的同步等待，约占单请求耗时的主要部分。当前保留它是为了拿到 broker 确认后立即把 outbox 标记为已发送；如果要进一步压低 P99，可以改成**异步 confirm + Relay 兜底重投**，代价是消息可能重复投递一次（消费端已按订单号幂等）。

## 4. 这份数据不能说明什么

- 不能说明能扛百万连接：这是单机短连接 HTTP，不是长连接网关；
- 不能说明集群下的表现：没有多实例、没有压 Redis 主从切换；
- 不能说明真实公网延迟：全部在同机局域网内。

写简历时可以这么写：

> 自研零依赖压测脚本，单机 500 并发下抢票接口 **966 QPS**、P99 **168ms**，1000+ 次请求零超卖、订单与库存最终一致；定位冷启动 JIT 导致首跑性能只有预热后的 1/4.6。

这个说法每个数字都能被追问，也都答得出来。
